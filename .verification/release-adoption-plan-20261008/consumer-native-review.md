Contrasté `main.go` de cada consumidor: las firmas y la configuración de `vegabuild`/`vegapreview` compilan contra el pin publicado; preview sigue condicionado al secreto, `ShareLinks` no se activa, no se añadió SSR ni `vegaauth`. `runtime-interim.json` registra **18/18** casos `passed=true`, imagen/binario/hook anteriores y fixture retirada. La variante positiva usa binario y hook empaquetados; monta solo datos y observador, sin tapar el binario ni el redactor. La variante negativa añade exclusivamente un mount que enmascara el hook redactor y deja el binario empaquetado, de modo que la diferencia negativa/positiva prueba el hook. `entrypoint-interim.json` registra **18/18** comprobaciones `passed=true`, la misma imagen/binario/hook, único mount `/pb/pb_data`, `tini`/Node/PB originales, parada del contenedor al salir PB, reapertura con PB health 200 y Node HTTP 404, `terminalContainerExit=0`, `cleanupExit=0` y fixture retirada. Los logs runtime/entrypoint vacíos son compatibles con éxito porque los runners escriben JSON y salen 1 ante una excepción; el recibo declara exit 0 para ambos.

Esta evidencia puede trasladarse **solo a la frontera backend** de una imagen posterior si el binario y hook extraídos vuelven a tener los mismos bytes y se cotejan configuración efectiva, variables de entorno, usuario, WORKDIR, ENTRYPOINT/CMD y argumentos, mounts con fuentes/destinos/modos y flags/rutas que afectan la carga del hook y los datos. El JSON actual registra principalmente destinos, no toda esa configuración futura. El 404 de Node demuestra arranque y ruta HTTP, no la UI Astro, autenticación completa ni assets/CSP 0.11.0; la nueva imagen/SPA necesita su propia comprobación. Esta revisión solo leyó artefactos; no ejecutó Docker, builds ni suites.
